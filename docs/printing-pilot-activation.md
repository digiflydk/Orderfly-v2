# Explicit printer activation before the first supervised testbon

Issue #524 fixes two actual preparation blockers: newly created printers are disabled and previously lacked authoritative queue metadata, while synthetic delivery correctly requires an active native printer. This change never activates a printer during deployment.

Fresh create now checks both the queue ledger and one bounded original-job row in the same authorized transaction, before any write. An orphan ledger or job rejects creation. Only a proven unused new printer identity receives a canonical revision1 empty ledger, atomically with configuration, audit and initial activity. Edits and legacy identities never receive backfilled metadata; missing legacy metadata remains blocked. Retries reread orphan state; audit/commit failures roll back the ledger with every other write.

The superadmin printer row exposes explicit **Aktivér** for paused/disabled printers with current edit permission. The dialog's **Kontrollér printkø** calls the existing scoped queue GET. It must return current same-printer/same-revision verified empty metadata. A separate **Bekræft aktivering** action obtains the existing server-issued `resume_empty` queue review, then calls the existing audited lifecycle `resume` with that receipt and exact printer/queue revisions. The server rechecks native policy, ownership, current queue, expiry, actor and receipt in its own transaction. No new activation authority or GET-as-authority is introduced. Nonempty/unknown/stale queues remain blocked.

Receipts live only within the action, never in DOM, storage or telemetry. Double submissions are guarded synchronously. Unknown/conflicting responses require overview refresh; there is no automatic write retry. Permission revocation blocks further requests. Successful activation advances the printer revision, making prior device credentials stale. Refresh, rotate the device credential, configure its new one-time password, then begin a fresh qualification. Do not create a pilot job while disabled or reuse qualification from the prior revision.

## Controlled operator sequence

1. After the coordinator verifies the actual deployment and authorizes a controlled window, open **Superadmin → System → Printere** (`/superadmin/printers`). Select the exact brand/location and a dedicated Star HTTP printer. Do not change the Wolt device profile.
2. For a new printer, create its disabled configuration with correct mC-Print2/3 and 58/80mm profile. For an existing printer with missing/unknown queue metadata, stop; this change does not invent history or initialize it.
3. Click **Aktivér**, then **Kontrollér printkø**. Proceed only if the UI verifies an empty queue. Click **Bekræft aktivering**. Refresh is automatic; an unknown response requires **Opdater oversigten** and native status inspection before any retry.
4. Open **Printeradgang**. Issue a credential if missing; rotate any old credential now stale after the printer-revision change. Basic username is `orderfly`; the one-time password goes only into the selected printer's protected configuration. Never put it in a URL, screenshot, GitHub or logs.
5. Copy **CloudPRNT-pilotadresse** from **Printeradgang** using **Kopiér printeradresse**. The shared setup block remains available for an already active printer and after credential rotation; it also appears in the activation dialog. It contains the current HTTPS origin and exact native brand/location/printer IDs, never a password or job token. The selected physical device uses this URL and Basic username `orderfly` with the separately entered new password. Configure a poll interval of at least five seconds. The ordinary `/api/cloudprnt/...` endpoint intentionally returns no-job and cannot print. Device settings are a separately authorized operator action; no code deployment changes them.
6. With printer native state active/current credential and the separately authorized configuration gate, use **Første testbon → Start testforløb**. In its ten-minute window enter **Operatørens navn eller ID**, **Modelnummer fra printerens mærkat**, **Installeret firmware fra StarIO-kontrol**, select **Vælg lokal dokumentation**, and truthfully check both onsite observations. The protected local capture is hashed, not uploaded. Click **Bekræft og klargør én testbon** once.
7. Before any physical output, the coordinator must separately authorize `ORDERFLY_PRINTER_CONFIG_WRITES_ENABLED=true` and `ORDERFLY_PRINTER_PILOT_OUTPUT_ENABLED=true` in the correct hosting environment and verify the device/session/revisions. Existing generic order-print output flags remain off. Preparing the job does not itself set either flag.
8. Expected exact progression: consumed qualification plus `queued` synthetic job → authenticated ready POST commits `offered` and returns one token → authenticated GET commits `download_started` before exact PNG bytes → strict DELETE200/OK commits `confirmed`. Other reported failures become `failed`; uncertain status becomes `unknown`. Subsequent polls return no-job. Same terminal result is idempotent; conflicting result and repeated GET are409.
9. Observe actual paper once and inspect width, Danish glyphs and cut. Device-reported confirmation alone does not mark physical compatibility verified. Record the evidence separately. Restore the controlled output window after the test through the coordinator's authorized process.

Stop on wrong scope/profile/revision,401,409,503, unknown delivery, timeout, incorrect physical device or Wolt interference. Never resend the same bytes to resolve uncertainty. The pilot pointer remains durable after terminal completion; another test requires a separately designed/reviewed reset or new identity, not deletion by this UI. A prior printer revision, revoked credential or deactivation must stop delivery.

Verification: focused actual write/queue-review/lifecycle tests cover fresh create→existing reviewed resume, orphan races, legacy exclusion and rollback. A real Chromium mobile-width test exercises explicit GET/review/resume, no mount I/O, scope binding, blocked/foreign queues, duplicate click, uncertain-response no retry, permission revocation, no receipt storage and no overflow. These are software tests, not real printer acceptance.
