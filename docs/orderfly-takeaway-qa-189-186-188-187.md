# Orderfly takeaway QA remediation, 28 September 2026

Scope: #189, #186, #188, #187. Branch from `main`. No production writes, merge, deployment or GitHub Actions were performed.

## Causes and changes

1. **#189, checkout accounting.** Checkout created the order as `Received` with `paymentStatus: Pending`. The Superadmin orders page summed every fetched document and hardcoded its status badge to `Received`. The older sales dashboard also counted every non-canceled document. Orders now start `Pending`; only a verified paid Stripe session advances them to `Received` in the same Firestore transaction as invoice, counters, customer totals and notification outbox. Both sales summaries count only `Paid` non-canceled orders; the attempt remains visible with its payment state. Expired sessions and confirmed cancel returns atomically release capacity, set `paymentStatus: Failed` and set `status: Canceled`. Repeat expiration and paid webhooks are idempotent. Settlement verifies tenant, session ID, currency and charged amount. An admin cannot move an unpaid order into preparation or completion.
2. **#186, promotion details.** Existing discount documents can carry Firestore timestamps in nested records and optional legacy date fields. The discount route passed raw brand/location/discount objects into a client component; the standard discount route serialized supporting records but not the discount itself and assumed every date had `toDate()`. Routes now serialize the complete props and tolerate absent or legacy date values. Saving and activation logic is unchanged. This is the code-level cause based on the server/client boundary; production server digest/logs were not available here, so the exact production exception still requires verification after deployment.
3. **#188, synthetic product.** The public catalog already excluded `isTestData: true`, but this legacy QA fixture was active without that flag. A narrow guard excludes the documented `QA-… Product TEST` naming pattern and `DO NOT PREPARE` descriptions from the menu, cart restoration and server checkout. The product document and historical order references are retained. Live menu inspection before deployment found this one exposed QA item at Esmeralda Amager; other brands and locations were not audited. Deactivation of that specific catalog record should be a separate authorized production data change after reviewing its identity and references.
4. **#187, Danish checkout.** Discount errors, date/time labels and calendar locale, bag removal, VAT and canceled payment copy use Danish. Stored fulfillment instants remain ISO and are formatted in the Copenhagen timezone. The inactive legacy `time-slot-dialog.tsx` is not used by checkout; `timeslot-dialog.tsx` is the active component.

## Tests and limitations

- `npm run typecheck`: pass.
- Focused Node regression suite: covers signed webhook success and duplicates, settlement rollback, cancellation race, discount reservation, pickup/delivery pricing, combos, minimum order, newsletter eligibility and stacking, synthetic product filtering and localized dates.
- Live read-only desktop UI before deployment: the documented QA product remains visible in Drikkevare on the currently deployed version. This branch is not deployed, so its UI behavior and mobile layout cannot yet be inspected on the live domain.
- Playwright browser tests were attempted locally, but the browser binary was absent and the Playwright CDN returned a truncated/invalid archive. They are not recorded as passing. The focused Node integration tests ran locally without GitHub Actions.
- Stripe sandbox success/cancel/expiry and merchant visibility against this branch require a deployed preview with Firebase and Stripe test credentials. None was available to this checkout. No claim of a completed paid end-to-end test is made.
- Existing order `ORD-671268` retains its audit history. The new sales filter excludes its `Pending` payment immediately after deployment. Reconcile its stored status only after checking its actual Stripe session server-to-server: if expired/unpaid, apply the normal verified expiration/cancel transition; if paid, settle normally. Never bulk-update pending orders or delete this record based solely on its display label.
- Inspect the three named promotion documents in the deployed preview and test code create/view/edit/apply/deactivate, newsletter consent and automatic product eligibility before release. Existing campaigns and activation were not altered by this PR.
