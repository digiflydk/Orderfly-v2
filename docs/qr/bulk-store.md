# Atomic QR bulk writer (#414, child of #399, coordinator #389)

Candidate server adapter. `createQrBulkStore(db, options).create(scope, {canonical,sha256,requestId})` performs actual writes in one Firestore transaction. It is not yet an exposed HTTP route or UI confirmation flow.

`scope` is a verified server `QrScope` (brandId, locationIds or company-wide null, actorId). A mandatory `authorizeCreate(scope, locationId)` callback must recheck the current authenticated native `orderfly.qr_codes:create` permission for every distinct requested scope, on every transaction retry and saved-result replay. The HTTP adapter owns authentication, binds the supplied scope to its verified actor, supplies this callback from server code, and never accepts scope/actor/callback grants from browser JSON. A SHA-256 digest is integrity/idempotency material, never permission.

The command contains exactly the three documented fields. The canonical v1 plan is reparsed, limited to 100 rows and revalidated through the shared CSV preview using server-derived scopes and the shared HTTPS/UTM policy. It must match canonical normalized content byte-for-byte and match the supplied SHA-256. All rows must be for the scope's single brand; mixed-brand batches are rejected. UI can group and separately confirm different brands, but must not present those as one atomic multi-brand import.

Inside the transaction, re-read brand existence and current native location brand/isActive before any result or write. Brand existence matches normal store creation behavior, allowing administrators to prepare codes for suspended brands; the public resolver separately requires an active/trialing brand. Missing/moved/inactive locations reject the batch. All collision and record reads occur before the first write.

Each row creates a normal `brands/{brandId}/qrCodes/{id}` record, immutable global `qrPublicCodes/{slug}` index and per-code `audit/{requestId}` row with action `bulk-create`. One receipt in the existing brand-scoped `qrRequests/{requestId}` namespace binds actor, action and canonical plan through SHA-256. No global cross-brand receipt or new collection/index/rule is introduced. Slug/code collisions reject the transaction; nothing is overwritten or silently skipped. A complete 100-row batch uses 301 writes in one transaction. New records have active status, revision 1, no expiry, and default design; custom design/expiry are outside this CSV format.

Same actor/request/content returns the original full result without new writes. Changed actor/action/content under the same brand request UUID conflicts. Permission/native-scope revocation still prevents replay. A transaction failure rolls every staged record/index/audit/receipt back. Random IDs generated by a retried callback may change before commit, but only the committed result is returned; a later lost-response retry uses the receipt.

Names are not globally unique in normal QR CRUD. Duplicate names within the same CSV brand/location are rejected by preview; pre-existing names may coexist. Uniqueness is enforced for immutable code IDs/public slugs. The UI must not promise an existing-name conflict policy that the store does not have.

## Integration and validation remaining

Root owns authenticated JSON HTTP preview/confirmation, current-native guard wiring, explicit confirmation and browser handling of same-key uncertainty/conflict. Never loop over ordinary `store.create` for a batch. Wire this writer once per confirmed single-brand plan; show success only after the atomic result returns.

`tests/unit/qr-bulk-store.cjs` executes the actual TypeScript with a transaction double enforcing read-before-write, create-only semantics and staged rollback. Cases include full/replayed/concurrent success, altered actor/content/hash, native revocation/moved/inactive locations, mixed brands, malformed plans, injected partial-write failure, ID/slug collisions and all 100 rows. This is an isolated adapter test, not a Firestore emulator or production-data test. Full repository typecheck, CI, independent exact-head review, real isolated/emulator integration, authenticated browser QA and deployment verification remain separate gates. No production operation was performed.
