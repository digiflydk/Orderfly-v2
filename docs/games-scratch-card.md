# Games · Scratch Card V1

## Scratch surface and redemption update

Every field must be scratched with touch, mouse or pen; there is no visible reveal button. Focused keyboard and assistive technology users can press Enter/Space on a field. Nonwinning fields display configured prize names (or plain "Prøv igen" text when a game has too few prizes), never decorative heart/star/diamond symbols. The mobile board keeps three fields per ticket.

Prize redemption now has independent checkboxes for restaurant, Orderfly website and external website. Existing saved `redemption` values are mapped when `redemptionChannels` is absent, so older campaigns continue to parse. A free item on Orderfly requires an active product selected from that brand; checkout verifies that this exact product is in the basket and discounts at most one base unit, without making toppings or an unrelated product free. Uploaded codes remain external to Orderfly Promotions and cannot select Orderfly redemption. Shared Promotions codes cannot be individually redeemed in the restaurant. External website use still requires the partner's server-side code validation/checkout and signed conversion callback; the Orderfly script alone cannot enforce a discount there. For a generated code shared between Orderfly and an external checkout, the signed callback checks Orderfly holds and deactivates the internal code atomically when the external order is confirmed; the external partner must coordinate validation before payment to avoid race conditions.

## Launch integration update (September 2026)

The campaign now supports generated unique Orderfly Promotions discounts, existing shared Promotions codes, and uploaded external codes. Uploaded codes **never create** a Promotions discount. Shared codes must be an active, matching percentage/fixed amount Promotions discount and are website-only. Shared code attribution is campaign-wide, not individual. Product prizes can be redeemed in Orderfly when an active product is selected, or externally when that checkout accepts the code. Existing Esmeralda prize settings remain restaurant-only until the brand chooses other channels. The restaurant amount-entry workflow is deferred to the brand admin phase; the former redemption widget is removed from the game editor.

Newsletter sync looks up the normalized email in Omnisend, returns without mutation when already subscribed, and only queues a subscription for an explicitly checked opt-in. An unsubscribed contact can renew consent only through a fresh dated opt-in under the existing consent rules. Prize mail is independent of newsletter consent and goes through the central Notification Platform template `orderfly.games.prize`; the old Omnisend prize event is no longer sent. Text and subject are editable in Games; the template receives brand name, logo, colors, code, prize and redemption mode. Operators must publish the template and verify the sender profile for each tenant before enabling email. Game admin offers a test mail with an invalid test code. Platform acceptance is not delivery confirmation; delivery/bounce feedback requires the central platform's status integration.

Operations configuration: `ORDERFLY_GAMES_EMAIL_ENABLED_BRANDS` is a comma-separated allowlist of verified brand IDs. `ORDERFLY_GAMES_NOTIFICATION_BRANDS` is a JSON object mapping each brand ID to `{"organizationId":"<UUID>","senderProfile":"<verified-profile>"}`; the shared Notification Platform endpoint and secret must also be configured. Until all are present, live play is blocked. The brand-scoped template must be published in the corresponding organization. Configuration and sender verification are external operational gates, not created automatically by saving a game.

Website placement: add an HTTPS origin (for example `https://www.example.com`) in the editor and paste `<script async src="https://<orderfly-host>/api/public/games/embed.js?brand=<slug>"></script>` into a Webflow custom code block or another site's HTML. The script creates a responsive iframe and passes the host page path. The iframe checks the browser referrer origin against the allowlist and enforces the campaign's page placement. Hosts that suppress the referrer cannot embed. Browser storage hides the game after a successful play for the configured days; server-side one-play-per-email still applies. Anonymous visitors cannot be reliably classified as new or returning customers across devices. The public config and rendered page omit shared codes and mail configuration.

Metrics stored in `gameEvents` are impression, open, start, completed scratch, and prize issued. The Games admin displays these alongside confirmed paid orders, revenue and purchase-per-completion. Browser events are approximate, while Orderfly conversion records are written in the same transaction as the Stripe paid-order settlement for generated discounts or a configured shared Promotions code. Only a verified paid transition is counted. Restaurant sale amounts are out of scope until brand admin is ready.

External checkout requires an **adapter running on the checkout provider's server**, in addition to the embed script. After verified payment, POST JSON `{brandId,orderId,code,amount,currency:"DKK",status:"paid"}` to `/api/integrations/games/conversion`. On a full refund send the same order/code with `status:"refunded"`. Set `x-game-timestamp` to Unix milliseconds and `x-game-signature` to `sha256=<HMAC_SHA256(secret, timestamp + "." + raw_body)>`. Configure the brand's >=32-character secret in `ORDERFLY_GAMES_PARTNER_SECRETS` JSON. The server checks a five-minute timestamp window, signature, campaign and issued uploaded external code or configured shared code; a unique uploaded code can be confirmed only once. A repeat notification for the same order is idempotent. Browser-only purchase signals do not count as paid conversions. The external provider must implement code validation/discount and send actual paid order amounts; this repository cannot install code into an unknown checkout automatically.

Deploy the composite Firestore indexes documented in `docs/games-firestore-indexes.json` to the **production data project** before using analytics, code lookup and outbox. Test on each target domain with a configured sender/template and test order; verify that refunded orders leave the paid dashboard and that no code crosses brand boundaries. Production activation remains gated on these integrations and review.

## User journey
Superadmin → Games → Scratch Card configures one to three tickets of three scratch fields each (older saved counts of 1–6 are still accepted). The editor suggests one ticket for one or two prizes, two for three or four, and three for five or more; an explicit ticket choice is retained while editing. Customers enter name and e-mail, may provide a phone number, and separately choose whether to receive newsletters. Newsletter signup is optional and never required to play. The server draws exactly one outcome per play, independent of the number of tickets. A winning board has three matching prize symbols on exactly one complete ticket (or all fields if a legacy game has fewer than three); other tickets have mixed symbols from the selected prizes, with plain no-win text if too few prize names exist. A nonwinning ticket never has three identical symbols. Each ticket is shown as a separate row of three on mobile and desktop. A scratch gesture reveals the result; keyboard users can press Enter or Space on the focused field. A winning voucher is stored atomically with the play; its code is placed in the central Notification Platform mail outbox. The customer is told the mail is queued, not that delivery is confirmed.

Esmeralda preset: Pizza 10%, Tiramisu 25%, Pommes frites 65%, each as a restaurant voucher. It has 3 fields, 3000 total plays, and placeholder 1000-winner caps per prize. These caps cause the realized distribution to differ once exhausted. Codes are never shown in the browser response. Test plays use separate test counters and generated test codes, never deplete live prizes or imported codes; test vouchers cannot be redeemed and are limited to one per e-mail. Administrator-test works before mail configuration. It sends no newsletter opt-in, and only queues a test mail if the brand mail integration is ready. The result screen says clearly whether a mail was queued. New e-mail addresses can be used for subsequent tests.

## Status and placement
Configuration is saved as `gameScratchDrafts/{brandId}` and starts in `draft`. An authorized manager can switch to `test` or `live` and deactivate it. Public endpoints return only `live` games. `GamePlacement` mounts on Esmeralda's homepage and checks `placement` (`all` or selected local paths) in both the public config endpoint and the play transaction. The standalone `/games/{brandSlug}` page always presents a live campaign. Draft/test is available in the authenticated admin preview with the actual form and server allocation. The legacy preview component remains visual only.

Live activation requires a configured central Notification Platform endpoint, an enabled brand ID, and a verified brand organization/sender mapping. Omnisend configuration is separately required for newsletter signups. It cannot be enabled merely by editing the campaign. No deployment or production data change is performed by this PR.

## Branding and content
Logo, background image, prize images and WOFF2 font can be uploaded by a company-wide website editor. Server checks bytes, decoded image formats, size limit 5 MB, and tenant-scoped permission. Files get immutable brand-scoped Firebase Storage names. Alternative HTTPS URLs are accepted. Accent and surface colors, headline, instructions, no-win text, optional phone field and newsletter consent wording are editable. Admin can switch between mobile 390px and desktop widths. Don't upload a font without rights to host it.

The admin editor groups settings into four steps: Spillet, Præmier, Udseende, and Test og udgiv. All settings remain in the same save form while switching steps, so a single save includes the full draft. The form delegates validation to the server and displays its error even when the invalid field is on another hidden step; native validation would otherwise silently block submission. The preview stays beside the settings on desktop. One, two, or three tickets correspond to 3, 6, or 9 fields; old saved counts remain editable. Status is visible beside the selected brand, while test/live controls and code operations are on the final step. Saving a draft does not change its status.

## Prize codes and redemption
A prize has a probability, cap, type (`item`, `percent`, `amount`), code mode (`generated`, `shared` or `uploaded`), and independent redemption channels (`restaurant`, `orderfly`, `external`). Paste or import a `.csv`/`.txt` file of at most 200 unique codes per operation after saving a prize as `uploaded`. Code import checks brand permission and immutable pool identifiers. Generated codes use cryptographic randomness. One code is reserved inside the same transaction as a play. For generated percentage and fixed amount prizes in live mode, the transaction creates an Orderfly `discounts` record with one use, brand and active locations, so the normal checkout eligibility/capacity controls apply. `item` prizes with an Orderfly product ID reduce one validated catalog unit in checkout, so a free Pizza code cannot reduce an arbitrary basket online. The restaurant redemption action still exists server-side for an eventual brand-admin workflow, but the editor does not expose that interface in this phase. Generated Orderfly discount redemption is enforced by checkout reservations. Test vouchers cannot be redeemed.

## Data and privacy
`gamePlays/{sha256(brand,mode,email)}` holds one participation per normalized e-mail and mode; name, e-mail, optional phone, result and explicit newsletter choice are stored. `gamePlayLimits/{sha256(brand,day,IP)}` caps public requests to 20 plays/day/IP; this is a basic abuse control, not proof of unique human identity. `gameVouchers/{sha256(brand,code)}` (or a per-play hash for shared codes) holds code, owner play, mode and redemption state. Uploaded codes are stored in `gameScratchDrafts/{brandId}/codes/{hash}` with an availability flag. `gameMailOutbox/{playId}` holds the e-mail delivery event. `gameConsentOutbox/{playId}` exists only for an explicitly checked newsletter box, with the exact visible wording and time. All business collections remain denied to client SDK by `firestore.access.rules`; access is through scoped server actions and validated public routes. Limit retention and implement an erasure workflow before production data policy approval.

## Mail operations
The existing authenticated `/api/internal/marketing/sync` worker processes the game mail and consent outboxes. Prize mail uses the central Notification Platform's `orderfly.games.prize` template and a brand-mapped organization/sender profile. An accepted request is not a delivery confirmation; ambiguous results remain in `uncertain` for manual investigation. Known rate limits retry with backoff. The separate newsletter consent sync uses Omnisend; subscribed contacts are left unchanged, and explicit opt-in can renew a dated unsubscribe. Prize email does not require newsletter opt-in.
