# Games · Scratch Card V1

## User journey
Superadmin → Games → Scratch Card configures one to three tickets of three scratch fields each (older saved counts of 1–6 are still accepted). The editor suggests one ticket for one or two prizes, two for three or four, and three for five or more; an explicit ticket choice is retained while editing. Customers enter name and e-mail, may provide a phone number, and separately choose whether to receive newsletters. Newsletter signup is optional and never required to play. The server draws exactly one outcome per play, independent of the number of tickets. A winning board has three matching prize symbols on exactly one complete ticket (or all fields if a legacy game has fewer than three); other tickets have mixed symbols from the selected prizes, with decorative symbols filling gaps. A nonwinning ticket never has three identical symbols. Each ticket is shown as a separate row of three on mobile and desktop. Scratch gesture or an accessible reveal button reveals the result. A winning voucher is stored atomically with the play; its code is placed in an Omnisend mail outbox. The customer is told the mail is queued, not that delivery is confirmed.

Esmeralda preset: Pizza 10%, Tiramisu 25%, Pommes frites 65%, each as a restaurant voucher. It has 3 fields, 3000 total plays, and placeholder 1000-winner caps per prize. These caps cause the realized distribution to differ once exhausted. Codes are never shown in the browser response. Test plays use separate test counters and generated test codes, never deplete live prizes or imported codes; test vouchers cannot be redeemed and are limited to one per e-mail. Administrator-test works before mail configuration. It sends no newsletter opt-in, and only queues a test mail if the brand mail integration is ready. The result screen says clearly whether a mail was queued. New e-mail addresses can be used for subsequent tests.

## Status and placement
Configuration is saved as `gameScratchDrafts/{brandId}` and starts in `draft`. An authorized manager can switch to `test` or `live` and deactivate it. Public endpoints return only `live` games. `GamePlacement` mounts on Esmeralda's homepage and checks `placement` (`all` or selected local paths) in both the public config endpoint and the play transaction. The standalone `/games/{brandSlug}` page always presents a live campaign. Draft/test is available in the authenticated admin preview with the actual form and server allocation. The legacy preview component remains visual only.

Live activation requires that the brand ID is explicitly present in `ORDERFLY_GAMES_EMAIL_ENABLED_BRANDS` and has a configured, enabled entry in `ORDERFLY_OMNISEND_BRANDS`. The first gate represents an independently verified Omnisend automation. It cannot be enabled merely by editing the campaign. No deployment or production data change is performed by this PR.

## Branding and content
Logo, background image, prize images and WOFF2 font can be uploaded by a company-wide website editor. Server checks bytes, decoded image formats, size limit 5 MB, and tenant-scoped permission. Files get immutable brand-scoped Firebase Storage names. Alternative HTTPS URLs are accepted. Accent and surface colors, headline, instructions, no-win text, optional phone field and newsletter consent wording are editable. Admin can switch between mobile 390px and desktop widths. Don't upload a font without rights to host it.

The admin editor groups settings into four steps: Spillet, Præmier, Udseende, and Test og udgiv. All settings remain in the same save form while switching steps, so a single save includes the full draft. The form delegates validation to the server and displays its error even when the invalid field is on another hidden step; native validation would otherwise silently block submission. The preview stays beside the settings on desktop. One, two, or three tickets correspond to 3, 6, or 9 fields; old saved counts remain editable. Status is visible beside the selected brand, while test/live controls and code operations are on the final step. Saving a draft does not change its status.

## Prize codes and redemption
A prize has a probability, cap, type (`item`, `percent`, `amount`), code mode (`generated` or `uploaded`), and redemption (`restaurant`, `website`, `both`). Paste or import a `.csv`/`.txt` file of at most 200 unique codes per operation after saving a prize as `uploaded`. Code import checks brand permission and immutable pool identifiers. Generated codes use cryptographic randomness. One code is reserved inside the same transaction as a play. For percentage and fixed amount prizes in live mode, the transaction creates an existing Orderfly `discounts` record with one use, brand and active locations, so the normal checkout eligibility/capacity controls apply. `item` prizes are restaurant only in V1; there is no product-specific checkout discount, so a free Pizza code cannot reduce an arbitrary basket online. Restaurant staff with company-wide `orderfly.discounts:edit` can enter a live code in Games to consume it once; this also deactivates an unused website discount, provided no checkout holds or payments exist. A website redemption is enforced by existing checkout reservations; restaurant redemption checks held/paid capacity to prevent double use. Test vouchers cannot be redeemed.

## Data and privacy
`gamePlays/{sha256(brand,mode,email)}` holds one participation per normalized e-mail and mode; name, e-mail, optional phone, result and explicit newsletter choice are stored. `gamePlayLimits/{sha256(brand,day,IP)}` caps public requests to 20 plays/day/IP; this is a basic abuse control, not proof of unique human identity. `gameVouchers/{sha256(brand,code)}` holds code, owner play, mode and redemption state. Uploaded codes are stored in `gameScratchDrafts/{brandId}/codes/{hash}` with an availability flag. `gameMailOutbox/{playId}` holds the e-mail delivery event. `gameConsentOutbox/{playId}` exists only for an explicitly checked newsletter box, with the exact visible wording and time. All business collections remain denied to client SDK by `firestore.access.rules`; access is through scoped server actions and validated public routes. Limit retention and implement an erasure workflow before production data policy approval.

## Mail operations
The existing authenticated `/api/internal/marketing/sync` worker also processes game mail and consent outboxes. Omnisend custom event `orderfly scratch prize` uses `origin: api` and string event properties `name`, `prize`, `code`, `redemption`, `mode`, `brandId`. An Omnisend automation must be created and enabled for that event and personalized with the `code` property; its template should say how restaurant or website redemption works and should exclude test mode from customer campaigns. The worker verifies the configured brand before sending. It marks dispatch as uncertain on ambiguous network outcomes to avoid sending a unique voucher twice; operations must inspect `gameMailOutbox` and Omnisend logs. Omnisend event acceptance does **not** prove an e-mail was delivered. The separate game newsletter consent sync uses the existing contact synchronization provider and respects dated unsubscribe behavior; a prize mail is transactional, independent of opt-in.

## Verification and release
Run `npm run typecheck`, `node --test tests/unit/games-scratch-card.cjs`, and `npm run build`. For browser QA, verify mobile touch scratching, reveal button, explicit opt-in default unchecked, test mode, no available uploaded code, repeat e-mail, campaign cap, restaurant redemption twice, and checkout discount eligibility at another brand/location. Firestore emulator/integration QA and a real Omnisend test mailbox are required before live activation. Configure indexes for prize pool (`prizeIndex`, `available`) and existing brand/code lookup as needed by the production Firestore project. Independent CI/review and PO acceptance precede merge. Production deployment and live verification are separate stages.
