# Games · Scratch Card V1

## Merchant restaurant redemption

`/merchant` is the merchant admin overview and shares the Orderfly admin shell, mobile header and navigation with superadmin. An unauthenticated staff member is sent to `/admin-login?next=/merchant`. Existing modules remain at `/superadmin/*` and are linked from the merchant menu only when the session has the matching permission. Their data operations retain independent brand/location checks; the portal navigation alone is never authorization. Merchant navigation omits platform-wide people, billing, system, Orderfly website and global loyalty settings. The merchant overview draws brand/location choices from the staff member's scoped native grants. A superuser entering `/merchant` sees the merchant shell; non-superusers retain it when following module links.

`/merchant/redeem` is the "Indløs kode" menu under Promotions. Grant `orderfly.games:view` and `orderfly.games:redeem` to merchant staff in the platform role policy. Read and redeem checks are scoped to the assigned brand and location on every request, including inside the redemption transaction. The page lists live, unique vouchers eligible for restaurant redemption and searches their code, participant name, e-mail and phone. The operator selects their restaurant, confirms the voucher and enters the total purchase amount including VAT, or zero for a prize without a purchase. The page is mobile friendly. Campaign editing requires the separate `orderfly.website` permissions.

Redemption checks voucher ownership, live mode, one-use state, the originating play, and any generated Orderfly discount plus active checkout holds inside one Firestore transaction. It deactivates the online discount, marks the voucher redeemed, records the restaurant location and actor, writes an audit entry, and creates an idempotent `gameConversions` record. Positive purchases are `paid` and count toward game conversions/revenue; a zero-amount prize redemption is recorded with `redeemed` status and excluded from purchase metrics. A code enabled for both channels can be claimed once in either; an active online checkout hold blocks restaurant redemption. Uploaded codes are never treated as internal Promotions discounts. Shared codes remain ineligible for individual restaurant redemption. Existing `discounts:edit` authority is not granted by this interface.

The merchant portal is hosted at `orderfly.dk/merchant`. The brand website may expose `esmeraldapizza.dk/merchant` as a redirect to that route so the first-party Orderfly session cookie and existing login remain valid; an iframe cannot share that session reliably. The merchant role must be assigned to an existing verified staff account before use. Brand voucher queries currently read all issued codes for a brand (campaign cap is 3,000); paginate and index search before substantially increasing campaign volume.

## Campaigns and participants (September 2026)

The Games overview separates ended campaigns from completed plays. For the selected brand and overlapping campaign dates, it shows lifetime participation, completed play events, paid orders attributed to game codes and revenue from those paid orders. Pending or canceled checkouts are not counted. Shared codes support campaign attribution, not attribution to a particular player. The original campaign includes older records without `campaignId`; other campaigns use indexed aggregate queries.

`Games` lists active, scheduled, paused, test, draft and ended scratch campaigns for the brands the signed-in operator can view. The original `gameScratchDrafts/{brandId}` remains the first campaign; its existing plays and metrics belong to that ID. New campaigns use independent document IDs in the same collection and carry `brandId`, `campaignName`, `startsAt` and `endsAt`. Creating a campaign copies visual/prize settings as a draft, resets caps and counters, does not copy uploaded code pools, and changes copied shared codes to generated mode so the old Promotions code is never silently reused.

The Games dashboard uses the shared admin cards and buttons. Its permanent all-brand, all-time strip shows total games and participant counts across every brand the current principal can administer. A visible brand selector and optional Copenhagen calendar date range scope the status cards and status counts. The date range includes campaigns whose configured active window intersects the selected calendar days; a legacy live game without dates starts at document creation, while a draft without dates has no searchable active period. Participant counts are lifetime totals for the selected campaigns, not participation within the selected dates. Status and text search further narrow only the list. Paused and test campaigns appear under Kladder with their own status labels. Creating a game always opens a dialog that requires an explicit brand choice, even with only one brand. The list and creation choices use the brand-scoped website grants; server writes enforce the brand authorization again. Each row links to the editor and campaign-specific participants. The participants page groups its fields into five desktop columns and stacked cards below the large-screen breakpoint, avoiding horizontal page scrolling; test plays remain excluded.

Start and end are ISO instants; the UI displays them as local date/time and the list formats Europe/Copenhagen. An empty start opens immediately on activation; an empty end stays open until paused/ended. The public page, config, event and play transaction all check the effective time window. End is exclusive. Status `live` with a future start appears as scheduled; an expired end appears as ended without a cron job. Pausing blocks new plays while retaining records. An ended campaign cannot be edited or reactivated; create another campaign instead. Activation and edits reject overlapping live time windows for the same brand. The transaction rechecks status and time before allocating a prize so a page left open across an end time cannot issue a late code. Prize caps and one-play-per-email are now keyed by campaign ID, so a customer can play a later campaign separately.

The scoped participant page lists live plays in batches of 50 with name, normalized e-mail, date, newsletter opt-in and actual Omnisend job state, start/completion, prize, voucher issuance/redemption, central mail acceptance/failure and paid conversion amount when a specific play is attributable. Test plays are excluded. “Mail accepteret” does not prove inbox delivery. A newsletter checkbox does not prove provider subscription: `synced`, unchanged existing contact, opted-out, waiting and failed are distinct. A platform superuser may reschedule a failed game consent after the brand is configured; the action rechecks brand/play ownership and never replays an uncertain outcome. Shared Promotions codes can only support campaign-level conversion attribution; a specific participant's purchase is not inferable from a shared code. Do not represent an unattributed shared-code purchase as a participant-level conversion. Historic plays without `campaignId` remain attached to the original campaign. The list queries only brands with company-wide website view grants, via server code; Firestore client rules continue to deny direct access. There is no public participant endpoint.

Uploaded codes are reserved within the selected campaign. New imports also register the brand/code hash globally and reject duplicates against the original code pool and issued vouchers. Existing uploaded code pools are not copied. Prize emails continue to read the originating campaign's branding and text even when another campaign starts. Checkout and signed external conversions carry `campaignId` for campaign reporting; already-issued unique codes can still be redeemed after the game ends according to their normal discount/code terms.

The generic `/api/public/games/embed.js` now waits for the frame's campaign identity before applying its browser cooldown and reporting a visible impression. The Esmeralda Webflow `/produkter` popup is a separately managed page-footer script: on release, update its early brand-wide storage check to wait for `orderfly-game-config`, key storage by campaign ID (retain the original brand-only key for the first campaign), and use the same campaign ID from `orderfly-game-played`. Publish Webflow only after the Orderfly deployment. Otherwise a visitor who played an earlier campaign could be hidden from a later one during the old cooldown period. Verify this with a fresh and a previously played browser.

**Release checks:** Verify the original Esmeralda participant rows, a scheduled game before/at/after its window, overlap rejection, distinct repeat participation in a later campaign, separate counters and winner caps, queued mail from an ended campaign, and attribution through actual paid/refunded orders. Confirm the production data project's single-field indexes and query latency with realistic participant volume. Retention/deletion policy and the central Notification Platform delivery/bounce view remain separate launch decisions. New campaigns use indexed server pagination (50 rows); the legacy first campaign still scans brand plays to include pre-migration rows without campaignId. Backfill those old rows and switch that path to indexed pagination before a large multi-campaign rollout. The new-campaign offset should become a cursor at high volume. Do not export names/e-mails or sync newsletters without a separate, explicit consent and access review.

## Scratch surface and redemption update

Every field must be scratched with touch, mouse or pen; there is no visible reveal button. Focused keyboard and assistive technology users can press Enter/Space on a field. Nonwinning fields display configured prize names (or plain "Prøv igen" text when a game has too few prizes), never decorative heart/star/diamond symbols. The mobile board keeps three fields per ticket.

Prize redemption now has independent checkboxes for restaurant, Orderfly website and external website. Existing saved `redemption` values are mapped when `redemptionChannels` is absent, so older campaigns continue to parse. A free item on Orderfly requires an active product selected from that brand; checkout verifies that this exact product is in the basket and discounts at most one base unit, without making toppings or an unrelated product free. Uploaded codes remain external to Orderfly Promotions and cannot select Orderfly redemption. Shared Promotions codes cannot be individually redeemed in the restaurant. External website use still requires the partner's server-side code validation/checkout and signed conversion callback; the Orderfly script alone cannot enforce a discount there. For a generated code shared between Orderfly and an external checkout, the signed callback checks Orderfly holds and deactivates the internal code atomically when the external order is confirmed; the external partner must coordinate validation before payment to avoid race conditions.

## Launch integration update (September 2026)

The campaign now supports generated unique Orderfly Promotions discounts, existing shared Promotions codes, and uploaded external codes. Uploaded codes **never create** a Promotions discount. Shared codes must be an active, matching percentage/fixed amount Promotions discount and are website-only. Shared code attribution is campaign-wide, not individual. Product prizes can be redeemed in Orderfly when an active product is selected, or externally when that checkout accepts the code. Existing Esmeralda prize settings remain restaurant-only until the brand chooses other channels. The restaurant amount-entry workflow is deferred to the brand admin phase; the former redemption widget is removed from the game editor.

Newsletter sync looks up the normalized email in Omnisend, returns without mutation when already subscribed, and only queues a subscription for an explicitly checked opt-in. An unsubscribed contact can renew consent only through a fresh dated opt-in under the existing consent rules. Prize mail is independent of newsletter consent and goes through the central Notification Platform template `orderfly.games.prize`; the old Omnisend prize event is no longer sent. Text and subject are editable in Games; the template receives brand name, logo, colors, code, prize and redemption mode. Operators must publish the template and verify the sender profile for each tenant before enabling email. Game admin offers a test mail with an invalid test code. Platform acceptance is not delivery confirmation; delivery/bounce feedback requires the central platform's status integration.

Operations configuration: `ORDERFLY_GAMES_EMAIL_ENABLED_BRANDS` is a comma-separated allowlist of verified brand IDs. `ORDERFLY_GAMES_NOTIFICATION_BRANDS` is a JSON object mapping each brand ID to `{"organizationId":"<UUID>","senderProfile":"<verified-profile>"}`; the shared Notification Platform endpoint and secret must also be configured. Until all are present, live play is blocked. The brand-scoped template must be published in the corresponding organization. Configuration and sender verification are external operational gates, not created automatically by saving a game.

Website placement: add an HTTPS origin (for example `https://www.example.com`) in the editor and paste `<script async src="https://<orderfly-host>/api/public/games/embed.js?brand=<slug>"></script>` into a Webflow custom code block or another site's HTML. The script creates a responsive iframe and passes the host page path. The iframe checks the browser referrer origin against the allowlist and enforces the campaign's page placement. Hosts that suppress the referrer cannot embed. Browser storage hides the game after a successful play for the configured days; server-side one-play-per-email still applies. Anonymous visitors cannot be reliably classified as new or returning customers across devices. The public config and rendered page omit shared codes and mail configuration.

Metrics stored in `gameEvents` are impression, open, start, completed scratch, and prize issued. The Games admin displays these alongside confirmed paid orders, revenue and purchase-per-completion. Browser events are approximate, while Orderfly conversion records are written in the same transaction as the Stripe paid-order settlement for generated discounts or a configured shared Promotions code. Only a verified paid transition is counted. Restaurant sale amounts are out of scope until brand admin is ready.

External checkout requires an **adapter running on the checkout provider's server**, in addition to the embed script. After verified payment, POST JSON `{brandId,orderId,code,amount,currency:"DKK",status:"paid"}` to `/api/integrations/games/conversion`. On a full refund send the same order/code with `status:"refunded"`. Set `x-game-timestamp` to Unix milliseconds and `x-game-signature` to `sha256=<HMAC_SHA256(secret, timestamp + "." + raw_body)>`. Configure the brand's >=32-character secret in `ORDERFLY_GAMES_PARTNER_SECRETS` JSON. The server checks a five-minute timestamp window, signature, campaign and issued uploaded external code or configured shared code; a unique uploaded code can be confirmed only once. A repeat notification for the same order is idempotent. Browser-only purchase signals do not count as paid conversions. The external provider must implement code validation/discount and send actual paid order amounts; this repository cannot install code into an unknown checkout automatically.

Deploy the composite Firestore indexes documented in `docs/games-firestore-indexes.json` to the **production data project** before using analytics, code lookup and outbox. Test on each target domain with a configured sender/template and test order; verify that refunded orders leave the paid dashboard and that no code crosses brand boundaries. Production activation remains gated on these integrations and review.

## User journey
Superadmin → Games → Scratch Card configures one to three tickets of three scratch fields each (older saved counts of 1–6 are still accepted). The editor suggests one ticket for one or two prizes, two for three or four, and three for five or more; an explicit ticket choice is retained while editing. Customers enter name and e-mail, may provide a phone number, and separately choose whether to receive newsletters. Newsletter signup is optional and never required to play. The server draws exactly one outcome per play, independent of the number of tickets. A winning board has three matching prize symbols on exactly one complete ticket (or all fields if a legacy game has fewer than three); other tickets have mixed symbols from the selected prizes, with plain no-win text if too few prize names exist. A nonwinning ticket never has three identical symbols. Each ticket is shown as a separate row of three on mobile and desktop. A scratch gesture reveals the result; keyboard users can press Enter or Space on the focused field. A winning voucher is stored atomically with the play; its code is placed in the central Notification Platform mail outbox. The customer is told the mail is queued, not that delivery is confirmed.

Esmeralda preset: Pizza 10%, Tiramisu 25%, Pommes frites 65%, each as a restaurant voucher. It has 3 fields, 3000 total plays, and placeholder 1000-winner caps per prize. These caps cause the realized distribution to differ once exhausted. Codes are never shown in the browser response. Test plays use separate test counters and generated test codes, never deplete live prizes or imported codes; test vouchers cannot be redeemed and are limited to one per e-mail. Administrator-test works before mail configuration. It sends no newsletter opt-in, and only queues a test mail if the brand mail integration is ready. The result screen says clearly whether a mail was queued. New e-mail addresses can be used for subsequent tests.

## Status and placement
The first configuration is saved as `gameScratchDrafts/{brandId}` and starts in `draft`; later campaigns have independent IDs as described above. An authorized manager can switch to `test` or `live`, pause or end a campaign. Public endpoints return only an effectively live campaign within its configured window. `GamePlacement` mounts on Esmeralda's homepage and checks `placement` (`all` or selected local paths) in both the public config endpoint and the play transaction. The standalone `/games/{brandSlug}` page always presents a live campaign. Draft/test is available in the authenticated admin preview with the actual form and server allocation. The legacy preview component remains visual only.

Live activation requires a configured central Notification Platform endpoint, an enabled brand ID, and a verified brand organization/sender mapping. Omnisend configuration is separately required for newsletter signups. It cannot be enabled merely by editing the campaign. No deployment or production data change is performed by this PR.

## Branding and content
Logo, background image, prize images and WOFF2 font can be uploaded by a company-wide website editor. Server checks bytes, decoded image formats, size limit 5 MB, and tenant-scoped permission. Files get immutable brand-scoped Firebase Storage names. Alternative HTTPS URLs are accepted. Accent and surface colors, headline, instructions, no-win text, optional phone field and newsletter consent wording are editable. Admin can switch between mobile 390px and desktop widths. Don't upload a font without rights to host it.

The admin editor groups settings into four steps: Spillet, Præmier, Udseende, and Test og udgiv. All settings remain in the same save form while switching steps, so a single save includes the full draft. The form delegates validation to the server and displays its error even when the invalid field is on another hidden step; native validation would otherwise silently block submission. The preview stays beside the settings on desktop. One, two, or three tickets correspond to 3, 6, or 9 fields; old saved counts remain editable. Status is visible beside the selected brand, while test/live controls and code operations are on the final step. Saving a draft does not change its status.

## Prize codes and redemption
A prize has a probability, cap, type (`item`, `percent`, `amount`), code mode (`generated`, `shared` or `uploaded`), and independent redemption channels (`restaurant`, `orderfly`, `external`). Paste or import a `.csv`/`.txt` file of at most 200 unique codes per operation after saving a prize as `uploaded`. Code import checks brand permission and immutable pool identifiers. Generated codes use cryptographic randomness. One code is reserved inside the same transaction as a play. For generated percentage and fixed amount prizes in live mode, the transaction creates an Orderfly `discounts` record with one use, brand and active locations, so the normal checkout eligibility/capacity controls apply. `item` prizes with an Orderfly product ID reduce one validated catalog unit in checkout, so a free Pizza code cannot reduce an arbitrary basket online. The restaurant redemption action still exists server-side for an eventual brand-admin workflow, but the editor does not expose that interface in this phase. Generated Orderfly discount redemption is enforced by checkout reservations. Test vouchers cannot be redeemed.

## Data and privacy
`gamePlays/{sha256(campaignId,mode,email)}` holds one participation per normalized e-mail and mode (for the first campaign, `campaignId` equals `brandId`); name, e-mail, optional phone, result and explicit newsletter choice are stored. `gamePlayLimits/{sha256(brand,day,IP)}` caps public requests to 20 plays/day/IP; this is a basic abuse control, not proof of unique human identity. `gameVouchers/{sha256(brand,code)}` (or a per-play hash for shared codes) holds code, owner play, mode and redemption state. Uploaded codes are stored in `gameScratchDrafts/{brandId}/codes/{hash}` with an availability flag. `gameMailOutbox/{playId}` holds the e-mail delivery event. `gameConsentOutbox/{playId}` exists only for an explicitly checked newsletter box, with the exact visible wording and time. All business collections remain denied to client SDK by `firestore.access.rules`; access is through scoped server actions and validated public routes. Limit retention and implement an erasure workflow before production data policy approval.

Prize mail uses the central Notification Platform's `orderfly.games.prize` template and a brand-mapped organization/sender profile. An opted-out contact is shown as suppressed, not as successfully subscribed. Prize email does not require newsletter opt-in.
