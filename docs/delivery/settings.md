# Levering settings

Owned by settings agent for #657.7–9. Configuration is preparatory: `deliveryDispatchEnabled()` always returns false. Saving `enabled: true` does not enable dispatch, change checkout, order a courier, or configure a provider binding. Provider availability/credentials and the final launch gate remain coordinator/Wolt integration work.

`GET /api/delivery/settings?brandId=...&locationId=...` returns effective settings, `brandSettings`, local overrides, inherited keys, brand/local revisions and edit capability. Omit locationId for brand defaults. `PUT` uses the strict discriminated command in `src/lib/delivery/settings/schema.ts`: `scope: brand` plus complete settings, or `scope: location` plus partial overrides and expectedBrandRevision. Both require expectedRevision. Omitted override fields inherit; `{}` resets all. Fields are replaced whole, including hours and date exceptions.

Native session verification and transactional `authorizeTransaction` enforce current catalog:view/edit and brand/location ownership. Brand operations require company scope; location-only grants cannot alter brand defaults. Writes compare revisions and create per-revision audit atomically. All transaction reads precede writes. An unknown write response must be resolved by a GET before another user-authorized save; do not automatically retry writes. Corrupt persisted scope/settings fail unavailable without exposing driver messages. Reads never create documents.

Canonical Firestore paths: `deliverySettings/{brandId}` and its `locations/{locationId}` subcollection. Both store schemaVersion 1, explicit brandId/locationId and revision. Each has `audit/{revision}`. No native location documents, policy documents, migrations or production records were changed. UI uses the existing authorized catalogue to select scope.

Hours are sorted, non-overlapping local minute ranges `[startMinute,endMinute)`. All seven days are present, Sunday=0. An empty date exception closes that date. Overnight periods must be split across two days/dates; exception dates replace the entire date. UTC instants are evaluated in Europe/Copenhagen using Intl, including both occurrences of repeated autumn hours and skipping nonexistent spring hours. Closed, disabled and paused reasons are distinct. The schedule check evaluates a requested instant only; the orchestration layer must additionally check preparation/transport timing, capacity, address/area and actual provider coverage.

Defaults are disabled, no provider, all hours closed. Preparation/transport/distance defaults are editable preparation values, not verified operating parameters or active customer prices. Maximum distance is inclusive; routes must be actual route meters from the routing module. Provider IDs are bounded identifiers so future providers do not require a settings schema rewrite. They are configuration only; the coordinator-owned production registry must verify provider availability and reject test providers before any dispatch. No provider secrets are included in this DTO.

Validation: internal `node --test tests/unit/delivery-settings.cjs`; `npm run typecheck`. Tests cover input bounds, invalid dates and overlapping hours, Copenhagen DST, exception closures, inheritance reset, local+brand CAS, parallel writes, native tenant/grant restrictions, revocation during retry, audit failure rollback, corrupt stored scope, anonymous access, origin validation, bounded body and duplicate query rejection. No production data or external providers are touched.

Pricing settings use `pricingRules: DeliveryPricingRules | null`, strict nested Zod fields plus the pricing module's cross-field validator. Null means no configured tariff. A location may inherit the brand tariff or explicitly set null; no sample prices are saved by defaults. Pricing maximum distance and operational maximum distance are separate constraints, both must pass coverage. Invalid/gapped bands and unknown economic fields are rejected before storage. Customer prices and settings remain preparatory behind the closed dispatch gate.
