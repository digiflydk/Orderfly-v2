# Managed delivery customer UI

The quote panel and tracking component are explicitly enabled by their parent. Disabled components render nothing; the server-provided managed-flow flag selects the managed checkout while pickup and legacy delivery retain their existing flow.

`useManagedDeliveryQuote` receives the actual quote action as an injected function, a complete request-identity string and current input. It creates a stable random 32-byte draft capability key in memory, suppresses duplicate requests, invalidates the current quote on address/cart/time/scope changes, and rejects late responses for older input generations. No private provider quote or economics are displayed. Opaque quote tokens remain in memory and are not placed in URLs, logs or browser storage.

The delivery price is requested automatically after a 700 ms pause once the required address/contact and checkout inputs are valid and checkout is not locked. Requests are serialized; edits during a request queue the latest identity and stale responses are discarded. The panel displays the server delivery fee, full total and available estimated delivery interval. It has no separate calculate-price button, delivery-price acceptance checkbox or switch-to-pickup button. The customer accepts the displayed valid total through the normal payment action, alongside the existing purchase terms.

Changing quote-bound inputs immediately makes the previous quote unusable. While a replacement is pending, the delivery fee and total are pending rather than zero, and payment remains unavailable. A changed price must be displayed before the customer can submit again; quote retrieval never submits payment automatically. Quotes with 60 seconds or less remaining, expired quotes, unavailable prices and mismatched quotes block payment. Failure or insufficient remaining lifetime exposes “Prøv igen” for a deliberate retry; there is no automatic retry loop. Errors preserve the customer's form and basket and explain the next action in Danish.

A failed courier confirmation replaces the address price preview. Once the quote state is unavailable, the success text “Leveringsprisen er beregnet. Vi bekræfter nu leveringen, før du kan betale.” is hidden, the preview fee and total are no longer shown in either summary or the payment button (the fee row reads “Ikke beregnet”, the total “Afventer leveringspris”), and payment stays disabled. Only the failure message and “Prøv igen” remain, so the screen never shows a calculated price next to a failure.

Failure messages come from the fixed public code returned by `customerQuoteFailure` (`src/lib/delivery/quotes/customer-failure.ts`). Provider “unavailable” reasons arrive prefixed (`provider_<reason>`) and are mapped to their customer-actionable public code: `provider_unsupported_schedule` → `unsupported_schedule` (“Vælg et senere leveringstidspunkt, så der er tid til klargøring og transport.”), `provider_closed` → `closed`, `provider_outside_area` → `outside_area`, `provider_invalid_address` → `invalid_address`. `provider_capacity` and `provider_unsupported_requirements` have no customer action and stay `delivery_unavailable` (“Vi kan ikke beregne leveringsprisen lige nu. Prøv igen.”).

## Scheduled delivery times (Wolt Drive)

Wolt Drive refuses a scheduled drop-off less than 60 minutes or more than 7 days ahead (`woltTiming`, limits in `src/lib/delivery/providers/wolt/schedule-limits.ts`). When the location's managed provider is Wolt, the server-projected public schedule (`readPublicManagedDeliverySchedule`) carries `scheduledLead: {minMinutes: 60, maxMinutes: 10080}`; no provider binding is exposed. `managedFulfillmentSlots` then offers only scheduled arrivals at least 60 + 15 minutes ahead and at most 7 days − 15 minutes ahead; the 15-minute margin covers quoting, payment and the clock moving while the customer decides. ASAP stays available while courier-now ASAP is possible (kitchen open and the first slot is the courier-now slot), because it is not sent as a scheduled drop-off; otherwise ASAP becomes the first lead-respecting scheduled slot. When the kitchen is closed, ASAP resolves to the first opening that satisfies the lead.

The server stays authoritative: `resolveManagedFulfillmentTime` derives the same limit from the stored `providerId`, and accepts an explicit time only at least 60 + 7 minutes ahead, so a slot picked a few minutes earlier stays valid; the 7-minute margin is above the 5-minute quote freshness window, so the time is still at least 60 minutes ahead when the booking is sent. While the kitchen is not yet open, the checkout keeps the ASAP time it first showed as long as the server still accepts it, instead of stepping to a later slot on every refresh. The Etage/dør field rejects control and invisible characters (e.g. emoji, soft hyphens) with a visible message, matching the server. A time that is too early or too far ahead is refused with `unsupported_schedule` before any provider call.

The final payment request still carries the exact displayed quote tuple and in-memory draft capability. The server revalidates the token, expiry, scope, cart fingerprint, revision, currency and total before consuming the quote. Removing a separate checkbox does not remove these checks or authorize payment from a background price refresh.

Tracking requires a matching order identity from an ownership-authorized server projection. Unknown booking is never presented as confirmed delivery even when payment is paid. Every delivery time shown to customers is an estimate ("Forventet levering: ca. …"); a rejected booking tells the customer to contact the restaurant and never shows the merchant-only failure reason or support code. HTTPS tracking links reject userinfo and unsafe schemes. Refresh is injected; no unauthenticated order endpoint is invented.

Internal browser acceptance for this UX must cover automatic pricing after valid input, no request for incomplete input, immediate invalidation on edits, stale-response rejection, expiry, visible updated totals before submission, stable capability, preserved form/cart and the absence of extra quote controls. Tracking retains foreign-identity and unsafe-link rejection coverage. Component fixtures do not prove live provider or payment behavior.

## Checkout integration

`CheckoutClient.managedDeliveryEnabled` defaults false and is supplied only by the server page. Managed delivery uses `requestManagedDeliveryQuoteAction`, invalidates quotes for contact/address/cart/time/discount changes, displays authoritative quote fee/total in both summary layouts and the payment button, and appends the exact accepted proof plus in-memory draft key as the final checkout argument. Pending quote prices are shown as pending, never as zero. Legacy pickup sends the original eleven arguments. Quote retrieval requires contact/address fields but does not require purchase terms acceptance; final checkout still does.

### Etage/dør (floor/door)

Managed delivery shows an optional single-line **Etage/dør (valgfrit)** input in the address group, between *Adresse* and *Postnummer* (`autocomplete="address-line2"`, max 60 characters, placeholder “Fx 2. th.”). It is separate from the *Leveringsinstruktioner* textarea (max 400). Legacy delivery and pickup do not show it, and a hidden value is never sent. The browser trims the value and omits it when empty; the server schema (`checkout-schema.ts`, `deliveryUnit`) trims again, caps it at 60 characters and rejects control/format characters.

`normalizeDanishDeliveryAddress` (`src/lib/delivery/quotes/address.ts`) turns it into the fulfillment's `dropoff.unit` (NFKC, collapsed whitespace). If the field is empty, the earlier fallback still applies: text after a comma in the street line (“Store Kongensgade 50, 2. th.”) becomes the unit. If both are given, the explicit field wins. The unit is not part of the routed/priced address. It is part of the quote-bound inputs: changing it revokes the displayed price and requotes, exactly like the address and the instructions. The server also rejects an accepted quote whose unit no longer matches (see `docs/wolt-drive-booking.md`).

The order's display address (`customerDetails.address`, used by the receipt, Merchant terminal, kitchen print and invoice) is built by `deliveryAddressLine` from the quoted unit, e.g. `Store Kongensgade 50, 2. th., 1264 København K`. An explicit unit replaces a comma suffix in the street line, so the receipt shows the same unit the courier receives. The customer profile address is unchanged. Browser coverage: `tests/unit/checkout-browser.cjs` (“managed Etage/dør …”).

Earlier Chromium runs covered the previous explicit quote controls and are historical evidence, not acceptance of the automatic-pricing UX. Current-head regression must verify the actual CheckoutClient, exact proof/fee submission and unavailable-price payment blocking. Existing live sandbox milestones are recorded in `native-browser-qa.md`; this UI change does not establish full courier lifecycle or production activation acceptance.

## Existing secure surfaces

Guest confirmation, authenticated Club history and Merchant order detail consume the existing authorized projections' `managedDeliveryTracking` field. No new public order lookup is introduced. Customer refresh reloads the current receipt/portal page through its existing authorization; Merchant refresh delegates to the existing scoped board refresh. Missing update timestamps remain “ikke oplyst”. History uses unique accessible heading IDs per order. Managed Ready orders expose kitchen readiness but no manual “Markér leveret” action; the server independently enforces this boundary.

Paid guest confirmation with an unknown booking now explicitly says delivery is not confirmed. Internal actual-component tests cover that state, null timestamp, two history entries, managed Merchant readiness and retained legacy paid-pickup progression/tablet layout. These fixtures do not establish live courier acceptance.
