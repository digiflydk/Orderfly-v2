# Central customer directory

The Customers page preserves the original customer records as its default tab, including brand and status filters, loyalty, last order, details, edit and delete. The directory is an additional tab. Both views read the same existing records; no customer records are deleted or migrated by this change.

The original records table now adds Games and purchases by merchant for each existing customer record. Game-only contacts also appear in that table with a distinct status and a read-only profile link. The original customer detail page shows played campaign names, dates, merchant purchase totals and Orderfly orders across authorized merchants. Campaign names are read from `gameScratchDrafts` for the play's brand and campaign; older plays fall back to the brand-id campaign. A customer without a valid matching email keeps the original record and order history, with no inferred Games link. Cross-merchant links are candidate matches by email and are visibly marked as such. Merchant sessions receive only their authorized source records and never see another merchant's activity.

The Customers view groups existing `customers` and live `gamePlays` by normalized e-mail. A superadmin sees one candidate identity across merchants. A merchant session receives only company-wide grants from `orderfly.customers:view`, and its rows use a brand-scoped identity key. The detail route resolves the key from freshly authorized records before querying orders. A guessed identity URL cannot bypass the tenant boundary.

Source documents remain in their original tenant collections. Orders, marketing consent, cookie consent, address, notes and loyalty are not copied between merchants. A Games opt-in is displayed as a fact about that play, not as permission to contact the person for another merchant. Test plays are excluded. Game-only contacts appear in the directory with zero sales unless a signed external purchase is attributed to that play. Existing checkout and booking customer records appear without a destructive migration or a backfill. The total includes paid native orders and paid external Games conversions with a unique play ID; refunded conversions and shared codes without a play ID are not assigned to a person. Native Games conversion events are excluded from the extra sum to avoid counting the same order twice.

Matching an e-mail is a candidate link, not verified proof that two records belong to the same person. The UI calls this out. A future verified customer account or manual conflict workflow should replace the candidate rule before using cross-merchant data for automated personalization.

The existing customer detail view now places contact details, this record's order statistics, cookie consent and per-merchant newsletter status in compact cards. Order and feedback histories occupy full-width tables with independent date and merchant filters. Game plays have their own table with campaign, merchant, play date, opt-in and attributed external purchases; the duplicate merchant order summary has been removed. The top 10 dishes table sums item quantities from paid, non-cancelled Orderfly orders with positive net payment. It keeps identical item IDs at different merchants separate. External conversions without item lines are excluded from the dish ranking.

The histories query only customer and game source IDs from the newly authorized directory for the current session. Each order lookup constrains both brand and customer ID; feedback uses its own brand grant, and newsletter contact records use the brand plus normalized email hash. A provider unsubscribe or suppression overrides old consent. Pending consent and absent records are shown as such, rather than claimed as confirmed subscriptions. Marketing consent is never merged across merchants.

The current directory reads all accessible customer, order, game and conversion documents during a page request. This preserves historical coverage, but needs paginated projections and indexes before the number of records becomes large. Merchant-specific customer detail pages have edit and delete controls on the original scoped customer ID. Only the five primitive fields required by the editor cross the Server Component boundary. The directory does not change checkout identity, marketing workers, order ownership or Firestore security rules.
