# Dully feedback in Orderfly

Dully invitations are an explicit external-order feedback source (`dully_order`). They never create commerce orders, customers, payments, print jobs, loyalty events or revenue. The pilot is restricted server-side to Esmeralda's existing brand ID. Administrative access requires the existing feedback permission and an active matching location.

## Source ingestion and identity

The Dully section accepts at most100 normalized JSON rows per import. It does **not** log into Dully or claim a direct API integration. An authorized browser agent/operator observes Dully and supplies these rows through Orderfly. `accountId` and `restaurantId` are stable operator-verified references, not guessed API identifiers. Configure them once from the actual account/restaurant and consistently reuse them. An existing mapping is immutable; the account/restaurant binding cannot be assigned to another location. The importer requires each row's restaurant reference to match it.

Fields: `externalOrderId` (stable Dully detail ID, not display order number), `orderNumber`, `externalRestaurantId`, `email`, `experienceType` (`pickup`/`delivery`), ISO8601 `orderedAt` and nullable `completedAt`, `status` (`completed`/`pending`/`cancelled`) and `paymentStatus` (`paid`/`unpaid`/`refunded`). Use the actual order creation time, not a future preorder service time. No address, phone, products or payment details are needed.

Identity hashes provider, brand, account reference and external order ID. Recipient, location, experience, number and creation time cannot change on repeat import; conflicts abort the entire batch. Status/payment/completion updates are allowed so pending and refunded orders can be reconciled. Identical reimports only renew source verification time. Every mutation records actor, scope, action and counts/source reference in `dullyFeedbackAudit`, without copying emails into audit. Sources imported before31October2026 Copenhagen midnight are ineligible. A cancelled, refunded, uncompleted or future-completed order cannot send or submit feedback.

The source reader must revisit open/preorder records and refresh refund/status information, not only newly created orders. Sending requires a source verified by import within24hours. This reflects operator/agent evidence, not a live Dully API check; refunds after the latest observation cannot be discovered without another import. Do not describe this as real-time synchronization.

## Test, approval and schedule

New mappings are paused. The test action queues a dedicated test source with a fixed server-side recipient `ok@esmeraldapizza.dk`. It uses the same `FeedbackMailProvider`, `orderfly.feedback.invitation` template, `orderfly` sender profile and central notification platform as existing Orderfly mail. It has a functional signed pickup/delivery form. Repeated test clicks reuse the stable source/event identity and do not duplicate an accepted or pending send. Once an accepted test expires, an explicit test request renews it with a new source/event identity. A transactional test-series pointer makes concurrent renewal clicks reuse exactly one new test; expired uncertain outcomes remain blocked. A known failed rejection can be retried using the same event key; unknown provider acceptance cannot be retried blindly.

The operator must inspect the received test and explicitly approve it. Server approval requires the latest test to be accepted by the mail platform and match the current mapping, language, both active questionnaires (including content), platform endpoint and organization. Acceptance means central mail queue acceptance, not inbox delivery. A changed configuration invalidates approval. Customer dispatch additionally honors the existing brand master `emailEnabled` switch. Explicit tests may send while it is off, without enabling it. Approval does not itself unpause sending: the separate resume action verifies the approval again. Root must not approve on the user's behalf before the user accepts the test.

The existing authenticated `/api/internal/feedback/send` heartbeat also runs the Dully worker. There is no GitHub development agent, GitHub runtime scheduler or OPENAI_API_KEY dependency. Each eligible order is due at21:00 Europe/Copenhagen on its completion day; orders completed after21:00 are due the next day. Overdue eligible sources catch up, including late imports and the initial31October batch after approval/resume. The heartbeat controls precision: execution is at the first available heartbeat at or after the due time, not a promise of exact-second delivery. A separate source-reading agent can import at21:00 without racing a one-shot empty-day marker.

The worker handles ten due records per invocation with a20second preparation deadline. Subsequent heartbeats drain the backlog. Leases serialize concurrent workers; final transactional claims recheck scope, activation, current question/settings fingerprint, approval, source status and freshness after provider preflight. Pausing defers pending sends; it cannot recall already dispatched messages. Known retryable provider rejections receive at most three automatic dispatch attempts. Preflight/configuration failures defer until corrected. Unknown provider acceptance or an expired dispatch lease becomes terminal `uncertain`; provider reconciliation is required, never automatic resend.

## Storage and feedback

Server-only collections: `dullyFeedbackConfigurations`, `dullyFeedbackBindings`, `dullyFeedbackSources`, `dullyFeedbackAudit`, `dullyFeedbackTests`, `dullyFeedbackTestSeries`. Existing blanket client Firestore deny rules cover them; no client credentials or rule/index migration is introduced. `dueAt` and scoped `historyKey` queries use single-field indexes. The UI returns at most500 recent records, explicitly marks additional history, and keeps controls/test status independent of the sample. Counts cover the displayed sample only. Each history row separates the stable external order ID and last source-verification time from worker activity time. A safe waiting-reason enum explains stale evidence, pause, missing approval, master-mail suppression, ineligible source, ordinary waiting, failure or uncertain acceptance without exposing infrastructure errors.

The Dully bearer token has a separate HMAC domain and is not interchangeable with order/booking tokens. It expires after30days. Public read and final submission verify source eligibility, immutable tenant/customer identity and active location; submission uses the existing questionnaire validation/activation lock and duplicate transaction. Test answers go only to `dullyFeedbackTests`, never customer feedback reports/public reviews/admin notifications. Real replies enter `feedback` with `dully_order` attribution and can enqueue existing admin notifications. Dully does not add reminder or thank-you mail automation in this release. Existing booking/order settings remain untouched.

## Verification and release

`node --test tests/unit/feedback-dully.cjs` covers synthetic import, authorization boundaries, immutable identity, concurrent idempotency, fixed test recipient, approval/fingerprint changes, Copenhagen winter/summer scheduling, backlog, stale refresh, pause/refund during preflight, bounded retries, uncertain acceptance, token separation, test-answer isolation and real-feedback/admin notification behavior. Existing mail endpoint/public page tests include the new worker and guest route. UI/browser validation is documented in `feedback-dully-admin-ui.md`.

No production data/email is written by tests. Follow AGENTS.md for local typecheck, relevant tests, independent review, current-main integration, PR release gates and live release verification. Production setup then requires explicit mapping, source ingestion, exactly one authorized test and user test acceptance before customer sending. A released feature is not proof that the source-reading schedule or customer sending has been activated.

## Online purchase wording and Danish questionnaire content

The public form uses order wording for Dully and commerce orders, including food, pickup/delivery and website experience. Booking and dine-in introductions retain visit wording. The thank-you page uses neutral wording suitable for both experiences. If a Dully questionnaire is unavailable, the message follows the verified source language instead of the generic not-found page.

Question labels and answer options come from the active questionnaire, not automatic translation. Maintain Danish pickup and delivery versions with Danish labels/options and a website-experience question. Updating either active version changes the Dully approval fingerprint, invalidates the previous approval and creates a new test series on the next explicit test request. Customer sending stays paused until the new test is approved and sending is explicitly enabled.
