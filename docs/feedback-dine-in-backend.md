# Public restaurant feedback backend (#793 / #794)

`getDineInFeedbackContext(brandSlug, locationSlug, language)` resolves exactly one active brand and location. Reads never create invitation, customer, settings or questionnaire records. The existing brand-specific booking questionnaire is reused; a deliberately disabled brand form does not fall back to a generic form. Esmeralda has a code-defined Danish restaurant fallback only when no brand-specific restaurant form exists. Other brands use their compatible existing booking/default form. Unsupported language/form returns unavailable.

The existing `ORDERFLY_FEEDBACK_TOKEN_SECRET` signs a domain-separated, 30-minute nonce binding brand/location IDs and slugs, language, question version and question hash. No new secret or configuration write is required. Rendering must be dynamic, never cache a guest nonce. `submitDineInFeedbackAction` checks the signed source and submitted fields, then rechecks active source and question configuration inside the transaction (including the existing version lock). The standard response validator and rating metrics remain authoritative; NPS is not a star rating.

A deterministic hash of brand, `dine_in` and nonce is the feedback document ID. Retries create at most one response. Anonymous feedback has empty customerId, no orderId, `sourceType: dine_in`, `answeredVia: qr`, private/moderated defaults and no email or customer writes. It uses the existing review settings and receipt after commit; duplicates, errors, disabled settings, missing links and ratings at/below threshold do not issue a new receipt. The normal thank-you redirect remains the fallback if receipt cookies fail.

Abuse limits: transactionally cap successful submissions at 30 per address/location/minute and 300 per location/hour. `feedbackDineInLimits` stores only HMAC bucket IDs and `{count, resetAt}`, with domain-separated address/location buckets. Address data is validated as IP, hashed with the existing secret, never stored raw. The per-address limit assumes the ingress proxy supplies a trustworthy forwarded address; the location cap cannot be bypassed by changing headers. This is a basic bound, not proof of restaurant attendance or comprehensive bot detection. Public link visitors can submit without a booking. Expired buckets are overwritten on reuse; no TTL/index/migration is deployed. Each new distinct address adds one small bucket record, so retention should be monitored.

Validation: `node --test tests/unit/feedback-dine-in.cjs` covers read-only resolution, tenant boundaries, disabled forms, token tampering/expiry, validation, configuration races, duplicate/concurrent submissions, transaction rollback, strict review policy and rate limits. Tests use synthetic in-memory I/O, not production feedback or email.
