# Wolt delivery creation and cancellation

Scope: #681, #682, #683 under #672/#657. Provider-only helpers; no checkout, payment, kitchen, printing or database implementation changes.

`createWoltDelivery` accepts a server-resolved binding and immutable quote. It validates matching brand/location/venue, a binding promise, provider expiry when supplied and a maximum local age of five minutes. Recipient coordinates/address come from Wolt's quoted dropoff location. `merchant_order_reference_id` is the Orderfly order ID (the `orders/{orderId}` document ID, e.g. `ORD-292972`), as Wolt Drive certification requires the partner's own order number on the delivery. The internal idempotency key stays the separate attempt digest (`originalAttemptReference`: sha256 of `delivery-original-v1`, brand, location, order ID), which owns the single original claim, `deliveryAttemptReferences/{attemptRef}` and every stored result; it is never sent to Wolt. One create per order is unchanged: the shared dispatcher claims the original attempt once, and the order ID is fixed for that claim. Parcel price is declared goods value, never the customer delivery charge. Cash, tips, alcohol/ID restrictions and handshake delivery are not enabled by this slice; unsupported flags fail validation rather than silently dispatching an unsuitable order.

## Parcel details (Wolt certification)

Each ordered line becomes one Wolt parcel with `count` = quantity, `description` = item name plus its chosen options and `price` = declared goods value **per unit** (Wolt multiplies it by `count`), in øre and currency `DKK` (managed delivery only runs for DKK brands). Wolt has no options field, so options are listed in the description, e.g. `Margherita (Ekstra ost, Uden løg)`; a description over 500 characters is cut and ends with `…`, so it never fails validation.

The checkout quote flow fills the shared contract's optional item fields `options` (max 100, each trimmed, max 150 characters) and `unitPriceMinor` (`src/lib/delivery/quotes/fulfillment-items.ts`) from the server-validated cart only (`validateCheckoutItems`: catalog names, toppings/modifiers and combo selections, checked prices). Options are the chosen combo products followed by toppings/modifiers (combo component modifiers read `Burger: Bacon`). The unit price is the charged line total divided by quantity: item offers and options included, cart-wide discounts and fees excluded; it is left out if the line total is not a whole number of øre per unit. The shipment-promise request sends the same `count` and `price` per parcel.

Both fields are optional so quotes stored before they existed still parse; such items are sent as before (name only, no price). They are part of the stored fulfillment, so `woltFulfillmentFingerprint` and the quote's content digest cover them: a create request whose options or prices differ from the quoted fulfillment is rejected as `quote_changed_or_expired`. Tests: `tests/unit/wolt-parcel-details.cjs`.

## Drop-off details (Wolt certification)

`dropoff.comment` keeps the drop-off details apart from the delivery instructions (`woltDropoffComment`): `Etage/dør: <unit>` on its own line, then `Besked: <instructions>`. Only the message is shortened to fit Wolt's 500-character limit, and the unit is kept whole. The unit comes from the checkout's separate **Etage/dør** field (max 60 characters), or, when that is empty, from text after a comma in the street line. The explicit field wins (`normalizeDanishDeliveryAddress`, see `docs/delivery/customer-ui.md`). The unit is not sent in the shipment-promise address.

The unit is part of the fulfillment's `dropoff`, so it is bound twice, in the same way as the street address. Within checkout, `quoteAddressBinding` (the draft's `normalizedAddress`, and therefore its `requestDigest`) includes it. A changed unit at payment fails as `quote_draft_changed`, so the customer must get a new quote. At booking, `woltFulfillmentFingerprint` hashes the whole parsed fulfillment. A create request whose unit differs from the quoted one is rejected as `quote_changed_or_expired`. Instructions are bound the same way, through the cart digest and the fingerprint. The fingerprint itself is unchanged: `unit` was already in the contract (nullable), so quotes stored without a unit still parse and match. Tests: `tests/unit/wolt-parcel-details.cjs`, `tests/unit/delivery-native-checkout.cjs`, `tests/unit/delivery-customer-quote.cjs`.


A 201 response must validate before being accepted. Both `id` (delivery identity) and `wolt_order_reference_id` (native identity for cancellation and webhook lookup) are retained. An invalid success response, lost response or `DUPLICATE_ORDER` remains unknown. An echoed `merchant_order_reference_id` that differs from the sent order ID is `REFERENCE_MISMATCH` and also remains unknown. Orders created before this change were sent the attempt digest; the PO confirmed (test phase, 2026-11) that such in-flight orders need no compatibility handling, so their late webhooks only stay pending. No general delivery/reference lookup endpoint is assumed. Recovery requires verified webhook evidence or operator resolution. Tracking must use HTTPS without embedded credentials. Missing ETA remains unknown. Provider prices use Wolt’s documented VAT-inclusive basis; the tax amount/rate is not invented. Initial create ETA must be displayed as preliminary according to the facade policy.

`bookWoltDelivery` is an optional wrapper around the **shared coordinator-owned repository**, not a second state machine. The repository must atomically reserve an intent before I/O, return dispatch permission to one caller only, freeze the validated request before awaiting storage, reject altered payload digests, and retain the claim through crashes. Repeated unresolved calls do not dispatch. Failed result persistence returns unknown; it never clears the reservation. If the common orchestrator already owns the reservation, call `createWoltDelivery` directly instead of claiming twice. Production integration must prove the actual repository semantics; the included tests use an isolated atomic fixture and do not establish Firestore correctness.

Cancellation resolves the native ID from authorized scoped storage. Known pickup start/completion disables automatic cancellation. A racing `INVALID_ORDER_STATE_TRANSITION` returns not-cancellable; only HTTP 200 with native `REJECTED` confirms cancellation. Transport failures, 202 and unexpected payloads remain unknown. Late cancellation stays disabled pending the specific Wolt agreement and fee acceptance policy. Fees are null when Wolt does not provide them. This adapter never issues a payment refund.

Internal verification: `node --test tests/unit/wolt-booking.cjs` and `npm run typecheck`. Fixture tests cover payload mapping, foreign scope, expiry, unsupported flags, malformed/lost/duplicate outcomes, concurrent dispatch, changed payloads, failed persistence, native identity and cancellation races. No GitHub Actions, live courier booking or production-data mutation is part of these tests.

## Native quote compatibility check (2026-10-26, #689)

The saved real sandbox ASAP and scheduled quote adapter outputs were passed to the creation request builder with their historical `fetchedAt` clock. Both mappings passed without network calls: six-digit fractional seconds and explicit `+00:00` offsets validate, the quoted coordinates/address are preserved, and the scheduled instant is copied unchanged. The regression test uses synthetic identity/address values with those timestamp formats. Real quote parcel responses contain nullable dimensions/value and empty tags; the facade builds creation parcels from validated fulfillment items instead of copying response-only parcel fields.

This is a compatibility check of recorded quote output, not a real delivery creation or cancellation test. No actual create response is available in that evidence set, so response mapping remains fixture-verified only. The cancellation endpoint and acknowledgement were rechecked against the official documentation; no contract drift was found. A verified test recipient and authorized sandbox lifecycle remain prerequisites for live create/cancel acceptance.
